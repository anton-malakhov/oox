# Scheduler Viewer

Автономный учебный проигрыватель распределения диапазонов между потоками.
Показывает девять моделей: Eigen + simple split, sharing + stealing, принцип
TBB Auto, битмасочный Rapid, Rapid с ленивой кражей остатка и четыре явные
политики Rapid Native (Auto, Simple, Static, Affinity).

## Калибровка другой машины — одна команда

Из корня checkout с этими локальными изменениями:

```sh
python3 tools/scheduler_viewer/calibrate.py \
  --output results/calibration-machine-a --threads 2 4 8
```

Скрипт сам настраивает Release build в `build-scheduler-calibration`, собирает
четыре измерительных targets и выполняет протокол. Папка результатов должна
быть новой: существующие данные никогда не перезаписываются. Текущий профиль
страницы тоже не перезаписывается.

Нужны Python 3.8+, CMake 3.18+, C++20 GCC/Clang, Git и build tool. Проекту нужен
oneTBB; CMake использует установленный пакет либо submodule. При первой
настройке CMake может загружать зависимости GoogleTest/Benchmark. Для просмотра
и получения `profile.json` Node.js не нужен; Node.js 18+ добавляет `report.json`
с проверкой математических моделей. Поддерживаемые пути: macOS/Linux,
x86-64/ARM64. End-to-end проверено здесь на macOS ARM64; Linux-ограничения
affinity/cgroup покрыты unit-тестами, но не нативным запуском на Linux.

### Что именно детерминировано

- Версия `scheduler-calibration-v2`, 10 фиксированных случаев, grain=2,
  64 прогревочных вызова, неизменные коэффициенты паттернов.
- Порядок блоков задаётся SHA-256 от seed и номеров блока, не версией Python PRNG.
  Порядок Rapid/битмаска заранее сбалансирован; позиция TBB вращается.
- При одинаковых параметрах получается тот же `plan.json` и `plan_id` на другой
  машине. По умолчанию seed=20261014, 9 парных повторов и 5 serial-процессов.
- План можно проверить без записи, сборки и замеров:

```sh
python3 tools/scheduler_viewer/calibrate.py \
  --output results/not-created --threads 2 4 8 --plan-only
```

**Не детерминированы** ОС, runtime work stealing, размещение потоков, частоты
и тайминги. Seed контролирует порядок запусков, не внутренний RNG Eigen/TBB.
Количество вызовов внутри таймируемого окна адаптируется к скорости CPU и
сохраняется в raw JSON: цель по умолчанию минимум 40 ms на случай, не одинаковое
число вызовов на всех процессорах. Результаты не обещают битовую повторяемость.

### Переносимое тело и ширина пула

По умолчанию выбран `--kernel arithmetic_v1`: зависимая цепочка определённых
64-битных unsigned операций с фиксированными константами. Результат защищён от
elision и проверяется независимыми reference vectors. Это синтетическое scalar
compute-ядро, не полноценная оценка памяти, SIMD или SpMV.

Старое `--kernel cpu_relax` оставлено отдельно. PAUSE на x86 и YIELD на ARM
не эквивалентны по стоимости, поэтому **не смешивайте эти профили и не делайте
по CpuRelax выводов о сравнительной вычислительной мощности разных ISA**.
Analyzer не сопоставляет предыдущие результаты с другим kernel/suite version.

Без `--threads` выбирается доступное подмножество 2/4/8 (либо 1 на одноядерной
среде). Явно можно запросить 1..64; выше нельзя из-за битмасочного прототипа.
Математический симулятор пока ограничен 32 работниками: native-замеры для 64
сохраняются, а недоступный модельный прогноз помечается отсутствующим, не нулём.
Для сопоставления машин задавайте одинаковые поддерживаемые ширины явно.

Запрошенная ширина пула выше доступного CPU-бюджета запрещена, если не указан
`--allow-oversubscription`. Это проверка заданной ширины, не гарантия числа
служебных OS threads внутри библиотек; single-worker fallback тоже зависит от runtime.
На Linux учитываются affinity и доступные cgroup quotas (best effort). CPU-набор
можно ограничить, например `--cpus 0-7`, если эти CPU уже разрешены процессу.
Это ограничение всего процесса и наследующих workers, **не закрепление каждого
worker за отдельным ядром**. На macOS такой опции нет. Для NUMA можно запускать
скрипт через выбранную пользователем политику numactl; она записывается, если
доступна. Governor/turbo/thermal policy скрипт не меняет.

### Параметры сборки и сохранённые артефакты

Для существующего build используйте `--build path --no-configure`: targets
всё равно пересобираются. Для нового toolchain передайте, например,
`--cmake-arg=-DCMAKE_CXX_COMPILER=/path/to/clang++` (не вместе с --no-configure).
Флаги не выравнивают автоматически разные компиляторы: версия, пути и flags
сохраняются для интерпретации результатов. Stats/PAPI/sanitizers запрещены.
Используйте single-config generator (Ninja или Unix Makefiles); Xcode и Ninja
Multi-Config отклоняются, чтобы случайно не измерить Debug вместо Release.
LD_PRELOAD/DYLD_INSERT_LIBRARIES требуют явного удаления пользователем;
переменные OMP/KMP/TBB/OOX, влияющие на сценарий, очищаются только у дочерних запусков.

Пакет содержит:

- `plan.json`, `status.json`, `environment.json` — протокол, состояние,
  CPU/ОС/affinity/quota, compiler/CMake/TBB metadata, git HEAD и dirty status;
- `configure.log`, `build.log`, `measurement.log`, `analysis.log` — этапы;
- `raw/` — stdout/stderr каждого свежего процесса, progress и полный JSON;
- `raw/sources.zip` — снимок относящихся к замеру исходников; хеши исходников и
  бинарников проверяются до/после прогона;
- `profile.json` — самостоятельный профиль машины, всегда при успешных замерах;
- `report.json` — дополнительный отчёт моделей, если есть Node.js 18+.

При ошибке сохраняются стадия, причина и частичные данные; успешный профиль
не выдаётся за завершённый прогон. Для повторного запуска выберите новую папку.
Небольшая служебная проверка скрипта, не полноценная калибровка:
`--repetitions 3 --serial-repetitions 3 --min-ms 5`.

Открыть конкретный профиль, не заменяя другие:

```sh
python3 tools/scheduler_viewer/run.py --profile results/calibration-machine-a/profile.json
```

Можно указать `report.json` для модельных ошибок. Сопоставляйте одинаковые
kernel, suite version, параметры и software stack; данные отражают всю среду,
а не только кремний. Полная аппаратная калибровка scheduler из этих микропроб
не следует: межъядерная когерентность, миграция и часть расходов остаются неизвестными.

## Запуск

Из корня репозитория:

```sh
python3 tools/scheduler_viewer/run.py
```

Нужны Python 3.8+ и современный браузер. npm, Node.js, внешние Python-пакеты,
интернет и сборка C++ для запуска не нужны. Скрипт открывает браузер и печатает
адрес. Сервер слушает только `127.0.0.1`, порт выбирается автоматически.
Для остановки нажмите `Ctrl+C` в терминале.

```sh
python3 tools/scheduler_viewer/run.py --no-browser
python3 tools/scheduler_viewer/run.py --port 8765
```

Запуск по абсолютному пути также работает: текущий каталог не важен.
Для сохранения настроек между запусками используйте постоянный порт;
browser localStorage привязан к адресу, включая порт. При недоступном
localStorage проигрыватель работает без сохранения настроек.

## Как смотреть

Для главного сравнения нажмите «Сравнить Lazy и Native Auto».
Lazy создаёт обычную задачу при успешной краже незарезервированного хвоста
самим вором. Native Auto продолжает обычную политику после Rapid-префикса:
владелец делит свой приватный буфер и публикует задачи, вор забирает их из
очереди. Native Static при полном захвате обходится фиксированными частями.
Native означает политику этого backend, а не нетронутый upstream Eigen.

Выберите планировщики checkbox'ами и паттерн нагрузки. Панели показываются
рядом, а на узком экране переносятся. Доступны запуск/пауза, шаг назад/вперёд,
перемотка, изменение скорости и переход к следующей передаче/разбиению.
Наведите указатель на диапазон, чтобы увидеть его границы и состояние.

Вертикаль — итерации, колонки — четыре или восемь потоков. Цвет обозначает поток,
насыщенность — состояние. Стрелка показывает передачу, черта — разбиение.
Пунктир в Native Auto/Affinity показывает границы приватного буфера владельца,
а не отдельные задачи в очереди. Счётчики различают обычные задачи и локальные
деления, не создающие задач.

**Это модель, не реальные инструментированные трассы и не бенчмарк.**
Один кадр — следующее событие каждой модели, а не общий момент времени.
Число кадров и число созданных задач не являются измерениями C++ реализации.
Затраты ОС, публикации, синхронизации и join не моделируются. Auto использует
учебный бюджет и упрощённый сигнал спроса, sharing — упрощённую адресную раздачу.
Реальные трассы открываются в отдельном режиме, описанном ниже.

`native-model.js` воспроизводит переходы исходного бюджета, пропорциональные
split-операции, private range buffer (восемь записей), относительную глубину и
упрощённый sibling feedback локальных политик. Выбор жертв и сигнал свободного
helper детерминированы и упрощены. Допуск потока заданий остаётся учебным, без
точной модели внешнего caller/fallback. История Affinity между вызовами,
конкурентный proxy lifetime и отмена не моделируются.
В Lazy-модели поиск бесплатен и другие workers получают ход до первой
резервации нового владельца. Поэтому количество краж и распределение работы
могут быть оптимистичнее, чем в реальной короткой записи.

### Несколько поступающих заданий

Выберите «8» и «Поток из четырёх заданий». В пул поступают четыре независимых
диапазона по 64 итерации: J1 с выбранной нагрузкой на такте 0, J2 равномерный
на такте 8, J3 с дорогими кластерами на такте 24, J4 с одной дорогой итерацией
на такте 40. Диапазоны имеют сквозные индексы [0,64), [64,128), [128,192),
[192,256); границы заданий отделены горизонтальными линиями. Статусы показывают
будущие, ожидающие, выполняющиеся и завершённые задания. Это один общий пул
внутри каждой панели, а не склейка независимых запусков.

Учебная политика поступления и допуска:

- Внешний отправитель не занимает поток пула; такт означает обход работников.
- Обычные модели публикуют новые задачи в очереди, даже если работники заняты.
- Битмасочная модель использует один общий запуск: следующее задание ждёт
  завершения предыдущего. Это ограничение выбранного сценария, не всех схем с масками.
- Lazy-модель допускает новое задание на доступных потоках, не прерывая занятые.
  Если свободных нет, оно ожидает. Ожидающие запуски имеют приоритет перед
  следующей попыткой кражи. Продолжения разных заданий могут выполняться одновременно.

Панели по-прежнему синхронизированы по номеру события, не по такту: одинаковый
кадр может показывать разные модельные такты и стадии поступления заданий.
Нельзя использовать эту картинку для сравнения задержек или пропускной способности.

## Устройство и проверки

- `model.js` — детерминированная модель событий без DOM.
- `app.js` — проигрыватель и SVG-отображение; не зависит от API чата.
- `index.html`, `style.css` — локальные ресурсы без CDN.
- `run.py` — сервер стандартной библиотеки с белым списком ресурсов.

Проверка сервера (Python), модели и интерфейсных обработчиков (Node.js,
нужен только разработчику для тестов):

```sh
python3 -B -m unittest discover -s tools/scheduler_viewer -p 'test_*.py'
node tools/scheduler_viewer/test_model.cjs
node tools/scheduler_viewer/test_native_model.cjs
node tools/scheduler_viewer/test_trace_state.cjs
node tools/scheduler_viewer/test_trace_ui.cjs
node tools/scheduler_viewer/test_flowchart.cjs
node tools/scheduler_viewer/test_lab.cjs
node tools/scheduler_viewer/test_lab_ui.cjs
```

Модель проверяется на точное однократное выполнение итераций и отсутствие
перекрытий/потерь в промежуточных состояниях. Это не тесты настоящего scheduler.

## Реальные C++ трассы

Ссылка «Реальные C++ трассы» открывает отдельный проигрыватель. Он использует
существующий парсер `benchmarks/scheduler_eval/tracing/model.js`, а не учебную
модель. Можно открыть JSON recorder'а через выбор файлов или передать каталог:

```sh
python3 tools/scheduler_viewer/run.py --traces results/real-viewer-tail-20261014
```

Каталог может содержать `EIGEN_STEALING.json`, `EIGEN_SHARING.json`, `TBB_AUTO.json`,
`RAPID_START.json`, `RAPID_AUTO.json` и `RAPID_NATIVE_{AUTO,SIMPLE,STATIC,AFFINITY}.json`
(хотя бы одну запись). У сервера нет
произвольного доступа к файлам по URL: только эти записи читаются при запуске и
безопасно встраиваются в страницу. Выбор файлов в браузере читает их локально.

Общий курсор движется по реальному относительному времени `steady_clock`,
а панели показывают состояние как в учебном режиме: колонки — потоки,
вертикаль — диапазоны. Насыщенные блоки активны, бледные завершены, пунктир
обозначает неизвестное состояние старой или неполной записи. Полные очереди
и незарезервированные остатки не восстанавливаются предположениями. Стрелки
показывают наблюдаемые передачи выбранного окна истории.
Время отображается общим ползунком в микросекундах.
Галочки управляют слоями наблюдения, а не отключают механизмы scheduler.
По умолчанию видна вся история до курсора; доступны последнее событие и окно
5 мкс. Счётчики показывают число событий до курсора / за выбранный вызов,
пустые слои недоступны. Создание части отмечается чертой в момент split,
отдельно от её последующей доставки или кражи. «Доставка задач» показывает
подтверждённую пару offer/take, не восстановленный полный состав очереди.
Журнал под панелью показывает время, источник, получателя и диапазон.
Если запись не содержит границ задачи или дорожки донора, наблюдаемая кража
остаётся в журнале и счётчиках с пометкой неизвестного диапазона. Координаты
стрелки в таком случае не выдумываются.
Сводка исполнителей не ограничивается последней стрелкой. «Следующая передача /
деление» пропускает промежуточные callback-события. Кнопка «Только Lazy и Native
Auto» оставляет нужную пару реальных записей.
Раздел диагностики под панелью показывает первый полностью наблюдаемый
интервал `resident_queue_scan` → `resident_range_probe` каждого worker.
Интервал, прерванный выполнением resident/обычной задачи, не соединяется.
Метки диагностические: интервал включает tracing и задержки ОС. Caller имеет
другой путь поиска. Старые записи этих меток не содержат.
Например, 100 мкс/с означает, что каждая секунда
видео раскрывает 100 микросекунд записи на обеих панелях. «Событие →» перемещает
общий курсор к ближайшей следующей отметке любой видимой записи. Число событий
больше не определяет длительность видео. Ноль — начало выбранного вызова в
каждом отдельном процессе; это не одновременно измеренные процессы.

### Записать новый запуск и сразу открыть

Для записи и аудита нужны Python 3.10+, CMake, C++20 toolchain и зависимости scheduler benchmarks
(включая oneTBB для исходного RAPID_START). Обычный просмотр по-прежнему не
требует сборки или внешних Python/Node-пакетов. Для уже настроенного build:

```sh
python3 tools/scheduler_viewer/capture.py --build build-scheduler-trace --threads 8 --shape tail
```

Скрипт пересобирает девять trace targets, последовательно записывает одинаковую
нагрузку, проверяет записи существующим аудитором и открывает viewer.
Каждый запуск создаёт новый каталог в `results`, сохраняя JSON, аудит,
команды и хеши бинарников. `--no-serve` только записывает и проверяет трассы.
Поддерживаются 4/8 потоков, `balanced`, `tail`, `hyperbolic`; параметры
`--tasks`, `--work`, `--iterations` управляют нагрузкой. Hyperbolic — синтетика,
не настоящий SpMV. Для первого конфигурирования можно использовать:

```sh
cmake -S . -B build-scheduler-trace -DCMAKE_BUILD_TYPE=Release \
  -DOOX_BUILD_BENCHMARKS=ON -DOOX_BUILD_SCHEDULER_EVALS=ON \
  -DOOX_ENABLE_EIGEN=ON -DOOX_ENABLE_TBB=ON \
  -DOOX_SCHEDULER_TRACE_TOOLS=ON -DOOX_SCHEDULER_EVAL_STATS=OFF
```

**Ограничения:** это реальные времена инструментированных запусков, а не
чистые бенчмарки. Per-callback tracing существенно вмешивается в короткую
работу. Отдельный парный замер без трассировки описан ниже. Три повтора
recorder выполняет последовательно; независимые поступления J1–J4 и смена
паттерна между ними пока поддерживаются только учебной моделью. Нельзя
объявлять speedup production-кода по этим записям.

### Модель рядом с записью

Откройте `/compare.html` и выберите реализацию. Слева отображается её учебная
модель, справа — реальная запись. Шкалы независимы: модельные события не
превращаются в микросекунды. Для автоматического сопоставления пока нужны
64 итерации, grain=2, 4/8 потоков и balanced/tail; для других параметров модель
скрывается, а не подставляется несовпадающий пример. Интенсивность хвоста
в модели теперь 16:1, как у recorder, но накладные расходы не откалиброваны.

- EIGEN_STEALING и EIGEN_SHARING — сохранённые экспериментальные partitioners
  на текущем Eigen-derived пуле. Это не исходные исторические бинарники.
- TBB_AUTO — настоящий установленный oneTBB. Для него видны вызовы тела,
  но не внутренние публикации и кражи TBB.
- RAPID_START — сохранённый битмасочный прототип, RAPID_AUTO — текущая ветка.
- RAPID_NATIVE_* — настоящий explicit-policy вход из `rapid_parallel_for.h`.
  Учебная модель слева показывает соответствующую политику с указанными выше
  упрощениями, а не обещание идентичного расписания.

В трёх новых trace targets scope `chunk` обозначает одну наблюдаемую итерацию,
не внутренний task scheduler. Отсутствие стрелок TBB не означает отсутствие краж.

## Лаборатория исполняемых блок-схем

Откройте `/lab.html` на том же сервере. Запуск по-прежнему одной командой:

```sh
python3 tools/scheduler_viewer/run.py
```

Движок `lab-engine.js` использует упорядоченную очередь событий, а не номер
кадра как время. Каждый worker исполняет граф из `take`, `split`, `steal`,
`tail`, `compute`, `wait`, `stop`. У блока есть переходы yes/no; выключенный
блок обходится по no без стоимости. Можно добавлять и удалять узлы, менять
переходы, выбирать начальный узел, задавать до 16 заданий и зависимости между
ними. Редактор — таблица блоков и связей с автоматической схемой, не drag-and-drop
редактор произвольного C++ кода.

Схема использует ромбы условий, прямоугольники действий, овалы начала/остановки
и подписанные ортогональные переходы. Выключенный узел имеет одну ветвь обхода.
У вычислительного блока отдельно показана проверка наличия работы. Произвольные
графы получают вертикальную раскладку с внешними возвратными линиями.

Порядок эксперимента: выберите заготовку → настройте нагрузку → «Зафиксировать
как базу» → измените механизм → «Запустить A/B». База и изменённый вариант
получают воспроизводимые seed и входы; при изменении нагрузки показывается
предупреждение. Конфигурация экспортируется в JSON, импортируется и сохраняется
в localStorage. Импорт не исполняет JavaScript.

### Что вычисляется

- Время завершения, полезная работа, processor-time обслуживания и простоя;
  нижняя граница по суммарной работе и зависимости самых дорогих итераций.
- Операции на одной очереди или одном tail-слоте сериализуются на явном
  ресурсе. Это модель обслуживания запросов, не симулятор cache-coherence/CAS.
- Воровство не затрагивает зарезервированную порцию. Успешная передача имеет
  отдельную стоимость migration. Локальные очереди ограничены; при заполнении
  split не публикуется, а входящее задание может ждать допуска.
- Поступления и job dependencies; join родителя предшествует допуску ребёнка.
- Фиксированные и удваиваемые порции, local-guided, историческая локальная
  sqrt-эвристика, heartbeat-inspired 20h. Последнее не реализация абстрактной
  машины из статьи и не наследует её теорем.
- Три сценария чувствительности служебных стоимостей ×0.5, ×1, ×2. Это НЕ
  вероятностный доверительный интервал и не гарантия монотонности результатов.

Обязательные проверки: уникальность исполнения итераций, конечность запуска,
валидность ссылок и зависимостей. Цикл без прогресса, отсутствие compute или
исчерпание бюджета событий дают ошибку, а не «ускорение». Тесты используют
независимый простой последовательный oracle, плотную сетку малых случаев,
крупные случаи с фиксированным seed и точные нулевые-overhead расписания.
Защита зарезервированного диапазона и учёт завершения встроены в движок:
обнулить их стоимость не означает удалить их семантику. Этот редактор не
проверяет последствия удаления атомиков или memory-order fences из C++.

### Реестр источников, а не выдуманная калибровка

`lab-evidence.js` хранит снимок двух существовавших исследовательских сводок:
`docs/PERFORMANCE_MODEL.md` внутри scheduler_eval и `RAPID_START_EIGEN_PAPER.tex`.
Импортированы 41 выделенный блок формул, 20 таблиц и полные исходные тексты
(включая оценки в прозе), а также 18 аннотированных карточек источников.
У каждого материала есть происхождение и статус. Это инвентаризация локальных
сводок, не заявление о повторной проверке всех внешних статей.

Часть первоисточников сверена: Hydra 2022 и присланные слайды (20–23),
Heartbeat PLDI 2018, granularity control PPoPP 2019, latency work stealing,
Hagerup и authored hybrid draft. В карточках отдельно отмечены источники,
сохранившиеся только как ссылки локальной сводки. Обнаружена библиографическая
неточность: Heartbeat 2018 — PLDI, не SPAA. Исходный TeX этим инструментом не менялся.

Теоремы work/span, постоянные 3.24/16.12 в границах, FSC и factoring находятся
в реестре, но не превращаются в наносекунды операций. Старые 49 нс относятся
к составному probe, а 75 мкс — к историческому timespan: ни то ни другое не
является универсальной стоимостью кражи. Исходные цены операций в движке
помечены **допущениями**. Кнопка измеренного профиля может заменить четыре
параметра прокси локальных микропроб и время тела; оставшиеся поля по-прежнему
не измерены. Статус выводится рядом с каждым параметром.

### Что ещё не реализовано

Нет полной аппаратной калибровки и независимой межсессионной/межмашинной валидации прогнозов,
NUMA/cache simulator, preemption/heterogeneous CPUs, reentrant memory-lifetime
протокола, полноценной модели nested fork–join, реализации всех алгоритмов
из библиографии или автоматического оптимизатора. Настоящие traces и эта
лаборатория остаются разными режимами. Сейчас инструмент пригоден для
проверки механизмов и чувствительности к допущениям, но не для публикации
прогнозов времени на CPU как измеренных результатов.

## Настоящий A/B и частично измеренные входы

Сначала собрать измеритель (Release, без `OOX_SCHEDULER_TRACE`):

```sh
cmake --build build-scheduler-trace --target \
  measure_scheduler_SERIAL_ELISION measure_scheduler_RAPID_AUTO \
  measure_scheduler_RAPID_START measure_scheduler_TBB_AUTO
python3 tools/scheduler_viewer/measure.py --build build-scheduler-trace \
  --output results/my-new-measurements --repetitions 9 --min-ms 40
node tools/scheduler_viewer/analyze_measurements.cjs \
  results/my-new-measurements/measurement.json --publish
```

`--output` должен быть новым каталогом. Для проверки повторяемости передайте
предыдущий `measurement.json` вторым аргументом analyzer перед `--publish`.
Скрипт проверяет совпадение хешей бинарников; разные сборки не выдаются за
same-binary повтор. UI читает компактный сгенерированный `local-measurements.js`.
Запись — CLI-действие; кнопка «Запустить A/B» на странице запускает только модель.

Протокол: 5 отдельных последовательных процессов для тела/микропроб, затем
9 блоков на каждом из 4/8 потоков. В блоке последовательно запускаются Rapid,
битмаска и TBB Auto; порядок Rapid/битмаска заранее сбалансирован, позиция TBB
вращается, порядок блоков перемешан с фиксированным seed. Каждый процесс
измеряет 10 случаев после 64 прогревочных вызовов. Startup исключён. Resident
limit полный, autocalibration отключена, pinning отсутствует. Каждая цифра —
среднее внутри процесса за минимум 40 ms, далее медиана между процессами.
Отношения строятся по парным блокам: median(A/B) не обязана равняться
median(A)/median(B). IQR не является доверительным интервалом.

Тело — синтетические `CpuRelax`-итерации, **не SpMV**. Корректность посещения
проверяется отдельным нетаймированным вызовом. В таймируемом теле нет trace hooks
и per-callback counters. Серийное тело измеряется без resident pools в процессе.

### Математические модели и границы идентификации

1. Сервис тела: `u_b = (S_balanced64,b - S_loop64)/64`, где `b` равен 100 или
   1000 повторов CpuRelax. Затем `w_i = u_b f(i)`. Это одноядерная оценка, не
   гарантия одинаковой скорости всех P/E-ядер под нагрузкой.
2. События: `start=max(worker_ready, resource_free)`, `end=start+c_op`.
   Модель включает сериализацию очереди и tail-слота, но не реальную когерентность.
3. Учёт: `P T = W + H + I`; нижняя граница `max(W/P, S_release)` учитывает
   зависимости заданий и неделимость отдельных итераций.
4. Независимый static-ориентир: `T_hat = L_empty(P,N) + max_j sum_{i in A_j} w_i`.
   Запуск и вычисления здесь складываются приближённо; перекрытие и неоднородность
   CPU не представлены.
5. Для событийного Rapid используются четыре proxy: hot PushFront → publish,
   hot PopFront → take, uncontended same-thread PopBack → steal, SC store/load
   → reserve. **Это не измерения межпоточной задержки.** Остальные шесть цен
   сохраняют статус допущений. End-to-end пустой запуск НЕ подставляется в
   стоимость публикации, поскольку включает активацию, тело и join.

Проверка моделей: шесть случаев на каждом числе потоков не используются для
вычисления `u_b`; оценивается MAPE относительно native medians. Это проверка
на отложенных формах/размерах в той же сессии, не независимая аппаратная
валидация и не доказательство переносимости. Параметры не подгоняются к этим
шести ответам. В чувствительности умножаются все служебные цены, не полезная работа.

### Наблюдения 14 октября 2026

Итоговый набор: `results/scheduler-lab-measure-20261014-confirm`; повтор теми же

есть `stlr`/`ldapr`. Невалидная цифра исключена, исходник и ERRATA сохранены.

  Выигрыш около 3.2×/2.9× воспроизвёлся в двух прогонах одной сборки.
