# Маленькая Rapid-группа в большом пуле

Отдельный opt-in стенд. Он не меняет настройки production-пула и не требует
TBB, Google Benchmark, визуализатора или дополнительных Python-пакетов.
Нужны CMake, C++20 GCC/Clang, системные threads и Python 3.10+.

## Один запуск на целевом CPU

Из корня репозитория, на машине с 128 доступными логическими CPU:

```sh
python3 benchmarks/scheduler_eval/rapid_group_experiment/run.py \
  --threads 128 --groups 2 4 8 16 32 64 --stress-workers 128 \
  --repetitions 7 --min-ms 100 --output results/rapid-group-cpu128
```

Скрипт собирает самостоятельный Release-проект, запускает тесты, диагностические
пробы и затем последовательные A/B-пары в свежих процессах. Выходной каталог
должен быть новым. `--jobs` задаёт параллелизм **только сборки**, не замеров.
Не запускайте одновременно другую сборку или benchmark. Per-thread pinning
не выполняется; внешние affinity/NUMA-настройки должны быть одинаковыми для A/B.

Для локального короткого исследования:

```sh
python3 benchmarks/scheduler_eval/rapid_group_experiment/run.py \
  --threads 4 8 --repetitions 5 --min-ms 40 --output results/rapid-group-local
```

`--plan-only` печатает детерминированный план без сборки и выполнения. Например,
план для 128 потоков можно проверить на ноутбуке. Реальные oversubscribed
запуски требуют явного `--allow-oversubscription`; они не заменяют замер на CPU128.

## Три независимые величины

- `workers`: весь пул, например 128.
- `group`: допустимый начальный домен `[0, group)`, включая вызывающий worker 0.
- `residents`: какие workers используют resident-ожидание. По умолчанию это
  весь пул, **одинаковый для всех сравниваемых размеров группы**.

Текущий Rapid API захватывает не более 63 помощников плюс caller. Поэтому
стенд принимает `group <= 64`, даже при `workers=128`. Группа 64 в пуле 128
**не называется полной группой**. `group` — верхняя граница: занятых workers
запуск не ждёт. Диагностика сохраняет фактическое число захваченных helpers;
их число не добавляется в горячее тело измерений.

## Политики и размещение

Все пять политик сравниваются при разных `group`:
`lazy`, `auto`, `simple`, `static`, `affinity`. Native-политики получают одно
корневое состояние для размера всего пула; подготовка делит его до числа
захваченных участников. Незарегистрированные в конкретной группе workers
не исключаются из обычного исполнения и краж.
Маленький диапазон или крупный grain также могут уменьшить число начальных
участников относительно `group`.

Для Native Auto/Simple дополнительно доступны:

| `placement` | Публикация из исполняющейся Rapid-команды |
| --- | --- |
| `local` | Обычная собственная очередь; красть могут все workers пула |
| `all` | Адресный round-robin по всему пулу `[0, workers)` |
| `outsiders` | Адресный round-robin только по `[group, workers)` |

Публикующие workers начинают обход с разных участков целевого множества.
У каждого свой cache-line-separated курсор; общего атомарного распределителя
нет. Это **размещение**, не обещание, что задачу исполнит именно адресат:
обычные кражи и bounded-queue fallback сохраняются. Адресат может быть занят.

Перехватывается существующий виртуальный `Schedule` в benchmark-подклассе
пула. После выхода из контекста Rapid-команды потомки снова публикуются обычным
локальным способом. Вложенный pfor внутри команды наследует её контекст.
Обе стороны A/B используют один бинарник и одинаковую benchmark-оболочку;
абсолютные времена не следует напрямую смешивать с другими benchmark-бинарниками.
Мы не подменяем affinity hints Static/Affinity и не превращаем Lazy в eager
sharing, поэтому новые размещения для этих трёх политик запрещены.

## Что проверяется

- Детерминированные небольшие диапазоны, нечётные размеры, различные grain,
  начала возле `SIZE_MAX`, два больших случая; независимый последовательный
  oracle и seed/case в диагностике ошибок.
- Вложенные вызовы, исключение и повторное использование пула.
- Прогресс nonmembers, пока **оба первоначальных владельца остаются внутри
  callbacks**: отдельно при resident-ожидании всего пула и только двух workers.
- Адресация индексов за границей 64; независимый oracle множества адресатов
  вплоть до 256. `--stress-workers 128` дополнительно создаёт настоящий пул 128.
- Отдельный diagnostic binary считает участие workers, захваты и адресные
  публикации. В timing binary этих счётчиков нет.

Скоростные нагрузки — 10 синтетических случаев: пустые loops 64/4096,
равномерные, тяжёлый хвост, кластеры, одна тяжёлая итерация. Используется
`arithmetic_v1`, grain 2, 64 прогревочных вызова. Это **не полный набор SpMV,
PBBS или приложений**, и не benchmark энергопотребления.

## Как читать результат

`report.json` содержит два вида сравнений:

- `group_size`: меньшая группа против наибольшей выбранной группы, размещение
  `local`, неизменный `resident_limit`.
- `placement`: `all`/`outsiders` против `local` при том же размере группы.

`time_ratio = B/A`, меньше 1 — быстрее. Сначала сравниваются соседние процессы
каждой пары; порядок A/B чередуется. Геометрическое среднее относится только
к десяти случаям этого стенда, а не ко всем приложениям. Все повторы сохраняются,
в том числе выбросы. IQR — разброс парных отношений, не доверительный интервал.

Рядом сохраняются `manifest.json`, `diagnostics.json`, сырые JSON/log каждого
процесса, хеши бинарников и архив исходников. Изменение бинарников или исходников
во время эксперимента отклоняет итоговый отчёт. Production-дефолт остаётся
неизменным независимо от результатов этой машины.

## Локальная проверка, 15 октября 2026

Apple M4 Max, без pinning; 4/8 workers, 5 свежих пар на сравнение,
310 измерительных процессов, resident limit всегда равен размеру пула.
Все visitation-oracles прошли. Полные сырые результаты оставлены локально
в `results/rapid-group-experiment-local-20261015/` (не добавлены в Git).

При 8 workers группа 2 против группы 8 с локальной публикацией дала
геометрические отношения времени: Lazy **1.136**, Native Auto **1.091**,
Simple **1.079**, Static **1.299**, Affinity **1.065**. При группе 2 адресная
раздача `all` против `local`: Auto **1.006**, Simple **1.001**.

Отдельные выигрыши есть: Lazy group=2 на loop64 — отношение **0.516**;
Auto group=2, `all` на tail64_1000 — **0.953**; Simple group=8, `all` на
tail4096_100 — **0.939**. Во всех пяти соответствующих парах направление
выигрыша совпало; это не независимое доказательство статистической значимости.
Универсального победителя нет, поэтому варианты сохранены для другого CPU.
Реальный 128-поточный замер на этом ноутбуке не выполнялся.
